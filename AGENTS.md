# Буквы по ГОСТ — работа через OpenSpec

Проект — планшетный тренажёр русского чертёжного шрифта для детей 7–11 лет.
Текущая продуктовая сборка:2026-11-07.56. Инструменты/документы не меняют этот номер.

## Где брать контекст

1. Последнее явное решение пользователя имеет приоритет.
2. Актуальные поведенческие контракты: `openspec/specs/`.
3. Состояние, карта кода, известные расхождения и границы доказательств:
   `openspec/project-analysis.md`.
4. Текущее изменение: `openspec/changes/<name>/`; завершённые — `changes/archive/`.
5. `PROJECT.md`, `PROJECT-PLAN.md` и `docs/history/` сохраняют историю и бэклог.
   Они не означают разрешение выполнить все описанные идеи. Старые сборки и
   отменённые подходы не подменяют актуальный контракт.

Полная прежняя версия этого файла сохранена побайтно в
`docs/history/agent-rules-before-openspec.md`; карта переноса —
`openspec/migration-map.md`. Не загружать весь исторический файл для каждой правки.
При расхождении кода и требований зафиксировать его; не менять контракт под баг.

## Как вести следующую работу

- Сначала `npm run spec -- context --json` и `npm run spec -- list --specs`.
  Использовать разрешённый CLI-корень, а не создавать OpenSpec в родительском каталоге.
- До продуктового кода создать/продолжить ровно одно изменение текущего объёма:
  проблема и capabilities → delta требований со сценариями → существенные решения
  design → задачи canary/реализации/проверок. Для малой правки артефакты короткие.
- Изменять существующую capability по её точному имени; MODIFIED сохраняет полный
  блок прежнего требования и сценарии. Не заводить отдельную capability на каждый баг.
- Явный запрос «сделай/исправь» уже разрешает реализацию в его границах.
  OpenSpec не добавляет повторного согласования к уже порученной работе.
  Запрос только анализа/плана и явный вызов `openspec-propose` — планирование;
  реализация начинается по последующему поручению пользователя.
- До расширения пройти маленький сквозной canary. Если подход даёт систематически
  неверный результат — остановить его, записать причину и защиту в материалах change,
  проверить новый подход на минимальном примере.
- Выполнять задачи последовательно; отмечать `[x]` только после фактического результата.
  `openspec status` проверяет наличие артефактов и не доказывает выполнение реализации.
- Проверить подходящий тестовый уровень и реальные пользовательские сценарии.
  `npm run spec:check` — формат/согласованность спецификаций, не тест продукта.
- При выполненном объёме синхронизировать delta через OpenSpec и архивировать change,
  затем снова проверить основные specs и архив. Не оставлять завершённое внедрение
  активной продуктовой задачей. Синхронизацию/архив считать завершёнными только по результату CLI.
- Не переделывать весь продукт под видом внедрения инструмента, анализа или исправления.
  Предложения, факты и реализованное поведение всегда различать.

## Критичные ограничения

- Только ГОСТ 2.304-81, тип Б без наклона; видимый контур — исследованный TTF,
  а не книжная/рукописная замена. Одноэтажная строчная а ожидаема.
- Нормативная форма и учебный порядок различаются. Демо и статическая инструкция
  разделяют порядок, оценка не проверяет направление/число штрихов/отрывы.
- Ради изменения стрелок/показа не менять model/outline/revision и хранилище.
  Реальное изменение геометрии требует совместимости/архива прежних работ.
- Сохранять raw ink. Перо/сглаживание — косметика, допуск — реальные CSS px.
  Копия пробы read-only, вмещает весь hitbox, без слежения за кончиком.
- Подсказка не блокирует быстрый reset. Проверять stale worker, pointerup/click,
  undo, сохранность других полей и исходных координат.
- Обычный idle finger-scroll работает при stylus-only; пересёкшаяся с pen-down
  ладонь блокируется до окончания. Не объявлять это аппаратной гарантией palm rejection.
- Схемы видны справа от демо в hero/dock; номера без кружков принадлежат своим
  параллельным стрелкам. Проверять реальные пиксели и смысловую привязку, а не только
  расстояния. К 2/к 2 — над верхней ветвью, В 2 — снаружи нижней части.
- По последнему решению владельца Я/я остаются цельными схемами; staged-эскиз отвергнут.
- Настройки общие для уроков, состав отдельный. Дев-попап прототипа разрешён,
  но не является защищённым аккаунтом. Ползунки не перестраивают страницу на каждом input.
- Бэклог не запускать: дальнейший замер времени, альбом/карточки, отдельная история
  рисования, новые диагностики/рекомендации. Существующий timing не удалять.
- Отдельную «новую попытку»/условия трёх зелёных результатов и перехода не домысливать:
  состояние и вопросы зафиксированы в анализе, нужен конкретный следующий scope.

## Проверки и локальные команды

- `npm test` / `npm run test:medium` / `npm run test:full`:3/9/32 файла;
  medium/full≥70% строк, функций и ветвей browser JS. Новые tests входят в каталог,
  новый range обязан иметь контракт в sliders.test.cjs.
- Миграции, geometry, промежуточная заливка у кончика, все 66 форм, рисунки и иконки
  имеют отдельные регрессии. UI-правку дополнительно проверять в реальном браузере.
- Не выдавать mock DOM, desktop mouse или размер окна за физический iPad/Pencil.
- Массовый визуальный просмотр букв начинать с общего атласа `editor/letter-atlas.html`
  (http://127.0.0.1:8782/, запуск в `editor/README.md`), а не с 33 навигаций по урокам.
  Атлас использует действующий WritingScheme; отдельные уроки проверять для интеграции
  и динамики. Для повторяющихся UI-вариантов сначала искать общий стенд или компактный
  fixture, сохраняя проверки реального пользовательского сценария.
- Runtime не имеет npm-зависимостей. `npm ci` устанавливает только dev-инструменты;
  OpenSpec CLI 1.16.0 устанавливается отдельно: `npm install -g @fission-ai/openspec@1.16.0`.
  CLI требует Node>=22.12, сервер/старые test-инструменты имеют собственное engine-ограничение.
- `npm run spec -- <command>` задаёт корень и отключает telemetry дочернего CLI.

## Работающий сервис и поставка

Существующий LAN на 8781 отдаёт только `concepts/`; `/healthz` проверяет readiness.
Не перезапускать ради docs/specs и не запускать дубликат. Не расширять web-root на
`openspec/`, `.agents/`, `editor/`, `references/` и исходники. При реальной задаче
запуска следовать глобальным правилам Local Projects Dashboard/native Terminal.
Ресурсы runtime имеют build/query-версии и offline-хеши; проверять совпадение
доступных ресурсов с проверенной версией. Для docs-only номер приложения не менять.
App Store-пакет, права на ASCON/PNG и установленный iPad/Pencil-пилот не закрыты;
не называть их завершёнными по прохождению Node-тестов.
