## Context
Рабочий продукт — локальный SVG/Canvas/JS-прототип,33 урока и 66 форм. Сборка 55, geometry4633c1e3. Политики накапливались в 103 длинных строках AGENTS и хронологических PROJECT/PROJECT-PLAN. Части старой документации описывают прежние сборки 46/51; состояние подтверждается исходниками и тестами.

## Goals / Non-Goals
Цель: рабочий OpenSpec и пригодный baseline с источниками и ясными границами следующей работы. Бэклог, новые схемы Я/я, условия перехода и упаковка iPadOS не входят в это изменение.

## Decisions
- OpenSpec 1.16.0 устанавливается глобально через официальный npm-пакет. Node>=22.12 требуется CLI; browser-продукт и его зависимости прежние.
- Codex core: propose/explore/apply/update/sync/archive; локальные skills в .agents, без правки shell startup или глобального профиля других проектов.
- npm wrapper задаёт корень проекта и отключает telemetry только для дочерней команды; персональная глобальная конфигурация не переписывается.
- Baseline:10 плоских предметных capabilities, существующие контракты с WHEN/THEN. Новый development-workflow проходит настоящий delta→archive; прошлые 55 сборок не превращаются в вымышленные завершённые changes.
- AGENTS становится компактной точкой входа, старый файл сохраняется побайтно в docs/history/agent-rules-before-openspec.md. PROJECT-PLAN не переписывается и не запускается.
- Продуктовая версия не увеличивается для изменений инструментов и документации. Проверяется неизменность хешей всех concepts-ресурсов и работа текущего LAN без restart.

## Risks / Trade-offs
- [Формально валидный текст может описать несуществующее поведение] → baseline сверяется с кодом/тестами; незакрытые или спорные пункты явно в анализе, не выдаются за выполненное.
- [Потеря старого правила при сжатии AGENTS] → исходный snapshot сохраняется, карта миграции привязывает группы правил к capabilities.
- [Случайное расширение объёма] → нет активных продуктовых changes; рекомендации/бэклог ждут нового поручения.
- [Процесс превращается в цикл подтверждений] → обычный запрос исправить/сделать сохраняет разрешение, а отдельный запрос исследовать/предложить остаётся планированием.

## Migration Plan
Canary init→change→strict validate→resume→archive выполнен во временном проекте. Затем init и baseline в изолированном Git-worktree, проверка схем/документов и полный регресс текущего продукта. После выполнения задач архивирование adoption обновляет development-workflow. Merge и push только проверенных файлов; runtime/service неизменны.
